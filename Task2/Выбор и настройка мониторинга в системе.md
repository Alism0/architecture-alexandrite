Выбор и настройка мониторинга в системе

# 1 Текущее состояние мониторинга

В настоящее время подключены Яндекс.Метрики к Online Shop, но они не обеспечивают полную статистику о взаимодействии клиентов с системой, так как теперь запросы создаются также через MES API.

Не отслеживается состояние компонентов - это может привести к снижению производительности и инцидентам, например, из-за недостаточно свободного RAM, низкой утилизации ресурсов процессора или закончившегося пространства на жестком диске.

# 2 Мотивация

Мониторинг позволит отслеживать показатели насыщенности и утилизации ресурсов и тем самым принимать меры до наступления критических значений. Настроенные алерты заблаговременно предупредят о приближении критических показателей.

Мониторинг предоставляет не только технические метрики, но и важные бизнес-метрики о взаимодействие клиентов с системой. Например, мониторинг запросов к MES API позволит отслеживать активность клиентов и дополнить данные собранные через Яндекс.Метрики для Online Shop

# 3 Выбор подхода к мониторингу

## 3.1 Подход для Online Shop

RED - данный подход позволит отслеживать метрики, которые отражают взаимодействие конечного пользователя с сервисом. 

Если во время взаимодействия запросы будут выполняться очень долго или завершаться ошибками, то пользователь останется неудовлетворен сервисом и компания может понести как материальные убытки в виде неполученной прибыли, так и репутационные, которые в конечно итоге отразятся на прибыли.

## 3.2 Подход для MES

Для данного сервиса потребуется настроить подходы USE и RED:

**3.2.1 USE**. В данном сервисе выполняются расчеты стоимости, обработка заказов и наблюдаются проблемы с производительностью в функционале операторов.

Необходимо начать отслеживать, чтобы установить связан ли сервис с проблемами процесса обработки заказов - это критически важно, так как сейчас клиенты неудовлетворены и компания теряет контракты.

Анализ полученных данных мониторинга позволит определить стратегию для оптимизации процессов в сервисе.

**3.2.2 RED** - так как в данном сервисе также надо отслеживать метрики взаимодействия клиентов с сервисом

## 3.3 Подход для CRM

Требуется настроить USE, потому что данный сервис взаимодействует через очередь с сервисом MES для обмена информацией о заказах, и таким образом является звеном, ошибки в котором могут приводить к проблемам с заказами.

Хоть и нет жалоб на работу данного сервиса, тем не менее важно настроить, так как возможно есть какие-то сейчас неочевидные проблемы, влияющие на процесс обработки заказов

## 3.4 Подход для Message Broker

USE подход. Критически важно настроить мониторинг для данного компонента, так как через него происходит обмен сообщениями об изменении заказов между MES и CRM. 

Настроив мониторинг удастся отследить насыщенность очереди, количество сообщений в очереди мертвых сообщений, показатели производительности. Тем самым получится установить, связан ли данный компонент с проблемами в процессе обработки заказов. Проанализировав полученные данные можно будет предпринять меры по оптимизации работы брокера сообщений.

Мониторинг состояния позволит предпринимать меры до возникновения проблем.

## 3.5 Подход для Shop DB, MES DB, File S3

Для каждого компонента необходимо настроить USE, так как это позволит отслеживать насыщенность и показатели, влияющие на производительность. 

Это позволит вовремя реагировать в случаях, когда, например, будет заканчиваться дисковое пространство, а также позволит оптимизировать выделенные ресурсы.

# 4 Метрики

## 4.1 Метрики Online Shop API

`Примечание:` в случае с RED, настроив метрику Response time (latency) и метки, можно  рассчитать все остальные метрики по идее

- `Number of requests (RPS)`
  - **Для чего:** позволит отслеживать нагрузку на сервис
  - **Требуются метки:** IP

- `Response time (latency)`
  - **Для чего:** позволит отслеживать время выполнения запросов пользователей
  - **Требуются метки:** Status Code, HTTP Method, Status Code, IP, UserId

- `Number of HTTP 200`
  - **Для чего:** позволит отслеживать количество ошибочных запросов
  - **Требуются метки:** Status Code

- `Number of HTTP 500`
  - **Для чего:** чтобы отслеживать количество ошибочных запросов. Например, всплеск можно интерпретировать как проблемы взаимодействия с одним из конечных компонентов или загруженность такого ресурса как RAM
  - **Требуются метки:** Status Code

## 4.2 Метрики CRM API

- `Memory Utilisation`
  - **Для чего:** позволит отследить уровень насыщения RAM и установить не является ли причиной сбоев в процессе обработки заказа из-за нехватки RAM
  - **Требуются метки:** -

- `CPU %`
  - **Для чего:** позволит отследить утилизацию ресурса и влияние на процесс обработки заказов
  - **Требуются метки:** -

## 4.3 Метрики Shop DB

- `Size`
  - **Для чего:** позволит отследить уровень насыщения и предпринять меры при превышении пороговых значений
  - **Требуются метки:** -

- `Memory Utilisation`
  - **Для чего:** позволит отследить уровень насыщения и предпринять меры при превышении пороговых значений, например, увеличить объем RAM
  - **Требуются метки:** -

## 4.4 Метрики Message Broker

- `Number of message in flight`
  - **Для чего:** позволит отследить уровень насыщения и установить не является ли причиной замедления процесса обработки заказа
  - **Требуются метки:** -

- `Number of dead-letter-exchange letters`
  - **Для чего:** позволит отследить заказы, при обработке которых произошел сбой, определить сервис потребитель, в котором произошел сбой, получить информацию о сбое
  - **Требуются метки:** -

## 4.5 Метрики File S3

- `Size`
  - **Для чего:** позволит отследить уровень насыщения и предпринять меры при превышении пороговых значений
  - **Требуются метки:** -

## 4.6 Метрики MES API

- `CPU %`
  - **Для чего:** позволит отследить утилизацию ресурса, влияние на процесс обработки заказов и влияние расчета стоимости изделия на производительность  
  - **Требуются метки:** -

- `Memory Utilisation`
  - **Для чего:** позволит отследить уровень насыщения RAM и установить не является ли причиной сбоев в процессе обработки заказа из-за нехватки RAM
  - **Требуются метки:** -

- `Метрики отражающие взаимодействие клиентов с сервисом`
  - **Метрики**
    - Number of requests (RPS)
    - Response time (latency)
    - Number of requests (RPS)
    - Number of HTTP 200
    - Number of HTTP 500
  - **Для чего:** необходимы бизнесу в дополнение к метрикам Yandex.Metrics для получения полного представления о взаимодействии клиентов с сервисом
  - **Требуются метки:** Status Code, HTTP Method, Status Code, IP, UserId

## 4.7 Метрики MES DB

- `Size`
  - **Для чего:** позволит отследить уровень насыщения и предпринять меры при превышении пороговых значений
  - **Требуются метки:** -

- `Number of connections`
  - **Для чего:** мониторинг позволит контролировать количеством соединений, которые могут влиять на производительность
  - **Требуются метки:** -

- `Memory Utilisation`
  - **Для чего:** позволит отследить уровень насыщения и предпринять меры при превышении пороговых значений, например, увеличить объем RAM
  - **Требуются метки:** -

# 5 План действий

Мониторинг будет реализован посредством стандартных средств окружения, инфры и встроенных в компоненты инструментов. Для Online Shop продолжить использовать Yandex.Metrics

**5.1** Развернуть и настроить Prometheus для сбора метрик

**5.2** Настроить метрики подхода USE для компонентов MES API, CRM API, MES DB, CRM DB, Message Broker, File S3 для отслеживания показателей утилизации, насыщения и сбоев. На основании полученной информации, установить места и причины проблем в процессе обработки заказов. Реализовать системными средствами окружения, в котором запущены компоненты

**5.3** Настроить сбор метрик взаимодействия клиентов с сервисом MES посредством системных инструментов инфры  

**5.4** Развернуть и настроить Grafana для визуализации метрик

**5.5** Создать дашборды для каждого компонента - это улучшит навигацию и консолидирует метрики по компонентам и выбранным подходам

**5.6** Настроить алерты на превышения пороговых значений насыщения, утилизации ресурсов, количества ошибок в период времени и т.д.

# 6 Показатели насыщенности

- Количество сообщений в очередях процесса обработки заказов. При превышении порогового значения увеличить количество потребителей
- Остаток свободного места на носителях под БД
