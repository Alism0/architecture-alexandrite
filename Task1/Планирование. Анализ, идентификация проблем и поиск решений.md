**Планирование: анализ, идентификация проблем и поиск решений**

# 1 Анализ проблем

## 1.1 Установленные проблемы

### 1.1.1 Проблемы с обработкой заказов

У заказов непонятное состояние, зависают в каком то сервисе либо теряются.
Это ведет к жалобам от клиентов: пользователей онлайн магазина и пользователей API. Это критическая проблема, так как компания уже начала терять контракты. 

### 1.1.2 Медленная загрузка Заказов на странице работы Операторов в MES 

В сервисе MES на странице работы операторов с заказами долгая загрузка Заказов
Для операторов это критически важно, так как от этого зависит выручка операторов

### 1.1.3 Возросшая задержка релизов

При обнаружение критические багов во время ручного тестирования, задерживается деплой релиза на прод до тех пор пока не будут исправлены баги. Время задержки в последнее время сильно увеличилось и может превышать месяц.

### 1.2.4 Нерелевантная статистика взаимодействия клиентов с системой

Бизнес получает неполную статистику об активности клиентов и заказах, так как Яндекс.Метрика подключена только к Online Shop, а теперь клиенты также создают заказы через MES API.

## 1.2 Потенциальные проблемы

### 1.2.1 Нет единого API для формирования заказов

Решение открыть API MES для приема заказов выглядит спорным. 

- Во-первых, MES предназначен для работы операторов

- Во-вторых, разные флоу для клиентов онлайн-магазина и API MES усложняет и запутывает архитектуру приложения

- В-третьих, с точки зрения ИБ дополнительное API для мониторинга

### 1.2.2 Расчет стоимости не расположен в отдельном stateless сервис

Рост нагрузки на MES API для расчета стоимости может аффектить процесс обработки заказов и работу операторов

### 1.2.3 Сущность заказа разделена между 2 БД 

Сущность Заказа разделена на две БД - необходимо поддерживать состояние в обоих. Изменение поведения в одном из сервисов может повлечь необходимость менять другие сервисы.

**2.5** Настройка трейсинга для прослеживаемости обработки заказа с целью определять участки процесса, в которых зависают и/или теряются заказы, и оптимизации процесса

**2.6** Начать поиск QA тестировщика для ускорения ручного тестирования и старта автоматизации тестирования

**2.9** Вынести функционал расчета стоимости в отдельный сервис для горизонтального масштабирования сервиса отвечающего за расчеты

**2.10** Реализовать автоматизированное тестирование

**2.11** Реализовать единый флоу обработки заказов от пользователей Online Shop и пользователей API MES

**2.12** Вынести логику обработки заказа в отдельный сервис, с которым будет взаимодействовать MES, CRM и Online Shop через брокер сообщений

# 3 Приоритеты

## 3.1 Проблемы по приоритетам

### 3.1.1 Проблемы в процессе обработки заказов

Сперва необходимо устранить проблемы в процессе обработки заказов, так как это влияет на самое главное: прибыль компании. Для этого требуется принять меры для идентификации мест возникновения проблем в процессе обработки заказов и установить точные причины.

Увеличение количества клиентов, обращающихся через онлайн магазин, и открытие API привели к росту жалоб. Вероятно возросшая нагрузка привела к переполнению очереди сообщений процесса обработки заказов, а также к низкой утилизации ресурсов таких CPU и RAM в сервисе MES. Неясно где именно происходит "зависание" или теряются заказы. Возможно происходит какое то необрабатываемое исключение.

Поэтому, чтобы разобраться требуется:

- Настроить мониторинг для отслеживания метрик насыщенности и утилизации ресурсов в MES, CRM и брокера сообщений
- Настроить логирование операций процесса обработки Заказов и  ошибок со стектрейсами
- Для отслеживания этапов в процессе обработки заказа и реагирования на задержки заказов, необходимо настроить трейсинг в сервисах принимающих участие в обработке: MES, CRM

Данные меры помогут установить места и причины возникновения ошибок, что позволит выработать решение над проблемами, возникающих в процессе обработки заказов.

Для достижения необходимо:

- Подготовить задачи DevOps инженеру для конфигурирования сервисов логирования, трейсинга и мониторинга
- Подготовить задачу DevOps инженеру по настройке мониторинга показателей утилизации и насыщенности в сервисах MES, CRM и брокере сообщений
- Подготовить задачу .NET разработчику на добавление логирования процесса обработки Закззов в сервисе MES
- Подготовить задачу Java разработчику на добавление логирования процесса обработки Закззов в сервисе CRM
- Подготовить задачу .NET разработчику на добавление трейсинга в этапы процесса обработки заказа в сервисе MES
- Подготовить задачу Java разработчику на добавление трейсинга в этапы процесса обработки заказа в сервисе CRM

На основании полученных данных необходимо будет проработать меры для устранения проблем.

### 3.1.2 Вынесение расчета стоимости в отдельный stateless сервис

Расчет стоимости - это долгая и затратная операция, занимающая от 2 до 30 мин на одну модель. Следует вынести данный функционал в отдельный stateless сервис для возможности горизонтального масштабирования.

Кроме того одной из возможных причин проблем в процессе обработки заказов может являться именно этап Расчета стоимости, так как это может приводить к низкой утилизации ресурсов сервиса MES и переполнению очереди сообщений с заказами для расчета стоимости. 

Настроенные мониторинг и трейсинг позволят отследить загрузку компонентов. А логирование определить ошибку, если такая возникает.

Если в результате анализа данных мониторинга, логирования и трейсинга подтвердится гипотеза о влиянии на процесс обработки заказов, то надо с высоким приоритетом взять в работу задачу по переносу функционала расчета стоимости в отдельный сервис для снижения нагрузки на сервис MES. 

Для вынесения функционала расчета стоимости в отдельный сервис потребуется:

- Подготовить .NET разработчику задачу на перенос функционала расчета стоимости из MES в отдельный сервис
- Подготовить DevOps инженеру задачу на развертывание кластера сервисов расчета стоимости и переключение маршрутов с сервиса MES на созданный кластер
- Подготовить задачу на удаление "рудиментов" в сервисе MES

### 3.1.3 Медленная загрузка дашборда на странице работы Операторов с заказами в MES

Запрос на получение Новых заказов выполняется у каждого оператора со значительно задержкой. Это свидетельствует о том, что на бэке долго выполняется подготовка данных для представления. Точную причину поможет установить настроенный мониторинг.

Так как все операторы запрашивают заказы в статусе "Новый", то для решения данной проблемы можно прибегнуть к кэшированию результатов запросов Заказов с учетом фильтрации заказов по статусам и пейджинга. Тогда всем пользователям бэк будет возвращать Заказы из кэша, не тратя время на долгую подготовку одинаковых ответов.

Для этого потребуется:

- Подготовить .NET разработчику задачу на реализацию кэширования Заказов в сервисе MES с учетом фильтрации по статусам и пейджинга

### 3.1.4 Создание единого API для формирования заказов

Реализовать единый процесс обработки заказов для клиентов Online Shop и клиентов API MES, путем создания единого API для формирования заказов вне MES API

Данное решение потребует проработки, но его реализация позволит:

- упростить архитектуру, благодаря тому что будет одинаковый процесс движения заказа
- улучшить безопасность, так как потребуется поддерживать функционал авторизации и мониторинг запросов для формирования заказов в одном сервисе 
- снизить утилизацию ресурсов для сервиса MES и упростить код сервиса MES
- разграничить домены, так как логика приема заказов будет сосредоточена в одном сервисе, а в сервисе MES будет сосредоточена логика работы операторов
- консолидировать метрики активности клиентов и обработки заказов

### 3.1.5 Сервис обработки заказов

Вынести логику обработки заказа в отдельный сервис, с которым будет взаимодействовать MES, CRM и Online Shop через брокер сообщений

Данное решение позволит сделать процесс обработки заказов более прозрачным и масштабируемым, а данные консолидированными. Изменения в других сервисах не поломают процесс обработки заказов.

Но данное решение весьма дорогое и требует больших изменений. На текущий момент данные изменения из разряда "Желательно".

Тем не менее собранные данные мониторинга могут послужить обоснованием для реализации данных изменений и повышения приоритета.

### 3.1.6 Расширение штата

Расширение штата позволит распределить возросшую нагрузку между сотрудниками и снизить bus factor.

Процессы найма QA тестировщика и DevOps инженера могут идти параллельно основной активности. 

### 3.1.7 Автоматизация процесса тестирования

Сократит время на прогон E2E тестов и удастся быстрее поставлять релизы.

Процесс автоматизации тестирования может идти параллельно основной активности
